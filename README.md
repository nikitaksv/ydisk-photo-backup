# Яндекс Фото — резервная копия на Go

Скачивание фотографий и видео из безлимитного Photoslice Яндекс Диска с локальным архивом, продолжением после остановки и непрерывным добором версий. Сценарий Photoslice основан на [PXSYS13/yadisk_backup](https://github.com/PXSYS13/yadisk_backup); MIT-лицензия автора сохранена в [LICENSE](LICENSE).

## Сборка и запуск

Нужен Go 1.23 или новее. Бинарные сборки, данные аккаунта и cookies в репозиторий не включены.

Windows / PowerShell:

```powershell
git clone https://github.com/nikitaksv/ydisk-photo-backup.git
cd ydisk-photo-backup
go build -trimpath -o photoslice-go-ready.exe .
.\start.bat
```

WebUI: http://127.0.0.1:8789 . Папка Windows-помощника по умолчанию: `D:\YandexPhotoBackup`. Для другого расположения:

```powershell
.\Start-Backup.ps1 -OutputDirectory E:\PhotoBackup
```

Linux / macOS:

```sh
go build -trimpath -o photoslice-go-ready .
./photoslice-go-ready serve -listen 127.0.0.1:8789 -out ./backup
```

Закрытие вкладки не останавливает сервис. «Остановить» прерывает текущую очередь; для полного выключения заверши процесс сервера. Повторный `start.bat` открывает уже работающий сервис для той же папки.

## Подключение аккаунта

1. В Windows запусти `export-cookies.bat`. В других системах открой страницу расширений Chrome / Edge самостоятельно.
2. Включи режим разработчика, выбери «Загрузить распакованное расширение» и папку `cookie-helper`.
3. Войди в [Яндекс Диск](https://disk.yandex.ru/client/photo) в том же браузере, открой расширение и нажми «Сохранить cookies.json».
4. Загрузи JSON в раздел «Настройки» локального WebUI, проверь вход и запусти архивирование.

Помощник использует браузерный Cookies API, включая HttpOnly, и сохраняет файл локально. После экспорта расширение можно удалить. Cookies дают доступ к аккаунту: не публикуй их. При истечении сессии или CAPTCHA обнови вход в браузере и экспортируй новый файл.

## Загрузка и качество

- **Превью и оригиналы скачиваются одновременно**, без последовательных проходов. Из 12 воркеров 6 предпочитают превью и 6 — оригиналы. Если в своей очереди нет готовой работы, воркер берёт задачу другой. При нечётном числе лишний воркер предпочитает превью.
- Недоступная версия не удерживает воркер: повторная попытка через 30, 60, 120, 240 секунд, затем не чаще чем раз в 5 минут. Срок и счётчик сохраняются в SQLite и переживают перезапуск. Общего интервала проверки качества больше нет. HTTP 429 по-прежнему останавливает новые запросы всех воркеров до окончания общей паузы.
- Лучшее доступное превью сохраняется независимо от оригинала. Если превью недоступно и нет оригинала, используется миниатюра. Все полученные версии хранятся отдельно; улучшение качества не удаляет старые копии.
- Фотографии имеют приоритет над видео. Когда готовых фотозадач нет и текущие передачи фотографий завершены, свободные воркеры берут видео; отложенные повторы фотографий не блокируют всю очередь.
- Каталог кластеров Photoslice обновляется **каждые 30 минут**, параллельно скачиванию. Содержимое новых, изменившихся и неполных кластеров загружается отдельно. Если API не сообщает ревизию, дополнительно проверяются до 64 стабильных кластеров по кругу, чтобы обнаруживать замены без изменения счётчика. Новые подтверждённые файлы попадают в очереди в течение 5 секунд. Ссылки на известные файлы также обновляются перед передачей, когда это требуется для их срока действия.
- **Серверный ZIP по умолчанию выключен**, поскольку Яндекс временно отключил эту функцию. Переключатель находится в настройках WebUI; CLI: `-zip-enabled=true` / `-zip-enabled=false`. Настройка сохраняется и меняется в WebUI без перезапуска.
- При включении ZIP сначала запрашиваются пачки до 500 оригиналов. Архивы скачиваются последовательно; свободные воркеры в это время помогают превью. Совпадающие имена и ограничение 8 GiB уменьшают пачку. Одиночные ZIP не запрашиваются. Если архив недоступен или в нём нет части файлов, эти оригиналы направляются на прямое скачивание. Успешная часть ZIP сохраняется независимо от пропусков.
- Проверяются положительный размер, CRC / SHA-256 и доступные размер/MD5 оригинала из API. Успех учитывается по каждой версии после сохранения на диск. Уже сохранённые версии пропускаются; скачанный, но не импортированный ZIP восстанавливается локально.
- Прерванная сетевая версия скачивается заново; продолжения с конкретного байта нет. Неподтверждённые записи проверяются отдельно и не занимают воркеры медиа.
- При запуске сохранённые архивы проверяются в фоне, без барьера перед скачиванием. Отсутствующая или повреждённая версия возвращается в очередь; завершение подтверждается только после этой проверки.

Загрузка работает постоянно до получения оригинала и превью каждого подтверждённого файла и подтверждения полного списка. Если Яндекс не отдаёт некоторые версии, очередь остаётся активной с отложенными повторами. «Остановить» отключает непрерывную загрузку; «Продолжить» снова включает её. `zip.bat -Trial -BatchSize 500` оставлен для отдельной диагностической пробы и требует включённого ZIP.

## WebUI

Компактный интерфейс в стиле TUI: «Обзор», «Файлы», «Журнал», «Настройки». Клавиши **1–4** переключают разделы, **R** обновляет данные. Пустые категории и неактуальные действия автоматически скрываются.

Обзор показывает число логических файлов с копией, лучшее качество, очередь ZIP, сетевую скорость, скорость новых файлов и место на диске. Скорость файлов переключается между секундой, минутой и часом. Прогноз относится к **первой копии каждого оставшегося известного файла**; он не обещает получение всех оригиналов и не подтверждает полноту аккаунта. В разделе файлов есть отдельный учёт наличия каждой из трёх версий и фильтры недостающих копий.

## Ошибки и ограничения частоты

MPFS использует HTTP 429 / код **394** также для состояния «скачивание архивов отключено». Этот конкретный ответ подготовки ZIP не является измерением RPS: сервер не выдаёт ссылку даже на небольшую пачку доступных файлов. Программа отдельно показывает недоступность серверного ZIP, сохраняет очередь и повторно проверяет функцию не раньше чем через 6 часов, пока флаг ZIP включён. Обычные медиа-загрузки продолжаются без дополнительной общей паузы. Остальные ответы 429 по-прежнему включают общий ограничитель.

HTTP 429 включает общую паузу всех работников с соблюдением `Retry-After`. Временное ограничение не считается отсутствием файла и не расходует обычные попытки. Пауза и сниженная частота сохраняются в SQLite после перезапуска. Уже начатые передачи могут продолжаться; после паузы запросы выпускаются постепенно.

Обычный начальный интервал — 500 мс для всех работников вместе. Автоподбор RPS постепенно снижает интервал на реальном трафике; при 429 возвращается к предыдущей ступени и прекращает разгон. Наблюдение без 429 не означает постоянную квоту Яндекса.

Проверка API ограничена 15 секундами. Медиа: до 8 секунд ожидания ответа и 8 секунд первого байта, до 30 секунд сетевого простоя после начала передачи, до 20 минут исправной передачи. Явные 404 / 410 сразу переключают качество; таймаут означает неподтверждённую доступность. По умолчанию 12 параллельных работников, допустимо 1–32. Метаданные не учитываются как скачанные фотографии.

## CLI

Примеры для Windows; в Linux / macOS используй `./photoslice-go-ready` и свою папку. Команды загрузки запускай при остановленной очереди сервиса: одновременная запись нескольких загрузчиков в одну папку блокируется.

```powershell
.\photoslice-go-ready.exe run -out D:\YandexPhotoBackup -workers 12
.\photoslice-go-ready.exe resume -out D:\YandexPhotoBackup
.\photoslice-go-ready.exe zip -out D:\YandexPhotoBackup -zip-enabled=true -batch-size 500
.\photoslice-go-ready.exe zip -out D:\YandexPhotoBackup -zip-enabled=true -batch-size 500 -max-batches 1
.\photoslice-go-ready.exe upgrade -out D:\YandexPhotoBackup
.\photoslice-go-ready.exe watch -out D:\YandexPhotoBackup
.\photoslice-go-ready.exe stats -out D:\YandexPhotoBackup -json
.\photoslice-go-ready.exe list -out D:\YandexPhotoBackup -filter missing-original
.\photoslice-go-ready.exe verify -out D:\YandexPhotoBackup
.\photoslice-go-ready.exe report -out D:\YandexPhotoBackup
```

`run`, `resume`, `upgrade` и `watch` запускают один непрерывный диспетчер. Существующие данные используются сразу, каталог обновляется в фоне раз в 30 минут. `zip` включает тот же режим с пакетными оригиналами, а `-max-batches 1` ограничивает диагностическую ZIP-пробу. Интервала `-interval` больше нет. Cookies по умолчанию читаются из папки данных; другой путь задаётся `-cookies`. Ctrl+C останавливает CLI.

`stats` и `list` поддерживают `-json`, `list` — `-offset` и `-limit` 1..100. Фильтры: `all`, `original-best`, `preview-best`, `thumbnail-best`, `missing-original`, `missing-preview`, `missing-thumbnail`, `no-copy`, `failed`, `pending`.

## Учёт файлов и неподтверждённых записей

Исправлена пагинация Photoslice: `clusters.fetched.items` может содержать полный индекс кластера на каждой странице, тогда как `resources.fetched` содержит только запрошенный диапазон. Обход теперь учитывает диапазон, а не длину полного индекса; страницы после первых 200 файлов больше не пропускаются.

WebUI, CLI `stats` и CSV отдельно показывают сохранённые файлы, подтверждённые файлы без копии и неподтверждённые ссылки Photoslice. Ссылка с `id/itemId`, размерами изображения или альбомами сама по себе не подтверждает доступность файла. Подтверждением служат данные файла (тип, размер или ссылки на медиа) либо уже проверенная сохранённая копия. Повторное получение метаданных сохраняет прежний идентификатор и не увеличивает число записей.

Прогресс, недостающие версии, очередь ZIP и ETA учитывают только подтверждённые файлы. Признак подтверждения хранится в индексируемом поле SQLite и обновляется при получении метаданных или сохранении копии; опрос статистики не разбирает JSON всех файлов заново. Старые базы обновляются автоматически без потери записей и версий. Старые ошибки неподтверждённых ссылок не считаются ошибками скачивания файла. Записи остаются в базе; фильтры `saved`, `no-copy`, `unconfirmed` и `records-all` позволяют проверить каждую группу. `all` показывает подтверждённые файлы.

Вместе с обновлением каталога каждые 30 минут выполняется отдельная проверка неподтверждённых записей: до 16 кластеров Photoslice, затем до 512 оставшихся обычных путей через OAuth REST API, с бюджетом до десяти минут и той же общей паузой HTTP 429. Она не занимает воркеры медиа. Подтверждённые файлы сразу попадают в рабочие очереди. HTTP 404 сохраняется как результат проверки метаданных, без удаления записи или утверждения о безвозвратной потере медиа.

Ручная проверка (бюджет до десяти минут): `photoslice-go-ready.exe reconcile -out D:\YandexPhotoBackup`. В JSON статистики `records` — все записи каталога, `confirmed` — подтверждённые файлы, `confirmed_no_copy` — подтверждённые без копии, `unconfirmed` — остальные записи. Поле `total` сохранено как совместимый с прежними версиями синоним `records`; для прогресса используйте `confirmed`.

## Способ загрузки Android: WebDAV

В разобранном APK Яндекс Диска 6.87.1 массовое скачивание создаёт очередь **отдельных файлов**, а не серверный ZIP. Путь: `DownloadFilesAction → DownloadCommand → ResumeDownloadHelper → TransportClient`, HTTPS GET через WebDAV, перенаправления и `Range`. Серверные ZIP — отдельный механизм веб-клиента. [Официальная справка Android](https://yandex.ru/support/yandex-360/customers/disk/app/android/ru/actions/download), [WebDAV API](https://yandex.ru/dev/disk/webdav).

Для дополнительного прямого получения оригиналов подготовлен WebDAV GET с OAuth. Положи токен с доступом к WebDAV в `oauth-token.txt` **в папке архива**, затем продолжи очередь. Значение токена не передаётся в аргументах команд, не попадает в статус, отчёты и журнал; Git игнорирует такие файлы. Cookies остаются нужны для списка Photoslice и превью. Токен выдаёт Яндекс для твоего приложения и аккаунта; программа не извлекает его из телефона. [Получение OAuth](https://yandex.ru/dev/disk/webdav).

При включённом WebDAV оригиналы сначала запрашиваются этим способом, затем — по доступным веб-ссылкам. Оригиналы и превью выполняются параллельно независимыми очередями. OAuth отправляется только исходному WebDAV-серверу и удаляется при перенаправлении на другой хост. Ответ 206 принимается только при полном диапазоне от нулевого байта; размер и MD5 оригинала по-прежнему проверяются. Возобновление с промежуточного байта пока не реализовано.

WebDAV-путь проверен автоматическими тестами на TLS-серверах. Работа с конкретным аккаунтом и доступность ресурсов безлимита требуют проверки с его OAuth-токеном; наличие обычного REST-токена не подтверждает права WebDAV. Для обычных файлов namespace `/disk` снимается перед обращением к корню WebDAV; `/photounlim` сохраняется явно. Недоступность мобильного способа не отключает получение доступных веб-ссылок.

## Формат архива и метаданные

Обычные версии сохраняются в `archives/<префикс>/<id>-<качество>-<хеш>.zip`; медиа внутри записывается без повторного сжатия. В ZIP входят неизменённые байты медиа, `metadata.json`, очищенные от секретов и подписанных URL метаданные API и доступный извлечённый EXIF-блок.

Серверные ZIP хранятся без перепаковки в `zip-batches/`, рядом — манифест с запрошенными файлами, проверенными записями, хешами, метаданными и пропусками. База `state.db` хранит прогресс, каждую версию и ошибки. В статистике `archives` — историческое имя числа сохранённых **версий**, `archive_files` — физические ZIP, `zip_archives` — пакетные ZIP.

Сохраняются полные доступные даты, доли секунды и смещение часового пояса, источник даты, подписи и остальные доступные поля API. EXIF сохраняется отдельно, когда доступен. Отсутствующий часовой пояс не выдумывается; исходные байты медиа не переписываются. Данные о файле остаются в БД и при отсутствии всех медиа-копий.

Каждые пять минут, а также после завершения или остановки создаются `report.csv`, `metadata.jsonl`, `summary.json`. После аварийного закрытия пересоздай отчёты командой `report`. CSV содержит одну строку на логический файл с качеством, датой и сведениями обо всех версиях.

## Проверка исходников

```sh
go test -timeout 60s ./...
go vet ./...
```

Используется внутренний API Яндекса, который может меняться. Программа сохраняет доступные серверу версии; недоступные файлы остаются в отчёте для повторных проверок. Полнота списка отмечается отдельно от успешности скачивания. Этот проект переносит сценарий Photoslice; функции обычного Диска, сортировки и дедупликации исходного Python-проекта не перенесены.
